# 0022. IFC reader: our own Part 21 reader, IFC geometry through the geometry port

- **Status:** Proposed
- **Date:** 2026-10-15

## Context

M1 imports IFC ([ADR 0021](0021-ifc-import-in-m1.md)): linked read-only references ([#140](https://github.com/hito-project/hito/issues/140)), native import of M1 elements ([#141](https://github.com/hito-project/hito/issues/141)) and Revit's exports ([#135](https://github.com/hito-project/hito/issues/135)). Spike [#139](https://github.com/hito-project/hito/issues/139) compared the two candidate readers named in [ADR 0016](0016-ifc-export.md):

- **ifc-lite** (`ifc-lite-core`, `-geometry`, `-processing`, MPL-2.0), a fast reader and geometry engine.
- **Our own reader**: a STEP Part 21 reader next to the writer of [#116](https://github.com/hito-project/hito/issues/116), with the IFC mapping and geometry in HITO and booleans through the geometry port ([ADR 0014](0014-geometry-kernel.md)).

Both read the same 118 public IFC files (47,650 elements: Revit 2011 to 2027, ArchiCAD, Tekla, IfcOpenShell and others, IFC2X3 to IFC4X3), with IfcOpenShell 0.9 as the reference. Both were fuzzed. The results, sources and corpus are in the Research Discussion linked from #139. The prototype is in the draft pull request for #139.

What the spike found:

| | Own reader (prototype) | ifc-lite 20.4.0 | IfcOpenShell 0.9 |
|---|---|---|---|
| Elements meshed, whole corpus | 98.5% | 99.5% | 98.7% |
| Elements meshed, Revit exports (25,861) | 99.2% | 100% | 100% |
| Volume agrees with IfcOpenShell (within 1%) | 98.2% | 97.6% | reference |
| Size | about 650 lines for Part 21, 1,750 for the IFC geometry | about 228,000 lines in core and geometry | |
| Missing | Advanced B-rep (NURBS), sectioned and tapered solids, IFC 4.3 linear placement | Almost nothing | |
| Panics, hangs, out-of-memory in 2 h of fuzzing | 0, 0, 0 (4.6 million runs) | 0, 0, 0 (630,000 runs) | |
| 221 MB Revit model (generated by repeating a real one) | 6.1 s on 1 thread, 335 MB | 9.9 s on 6 threads, 1.1 GB | 3 min 52 s on 6 threads, 2.6 GB |
| 343 MB ArchiCAD model | 4.3 s on 1 thread, 446 MB | 2.8 s on 6 threads, 753 MB | 1 min 10 s on 6 threads, 2.3 GB |

Other findings:

- **Revit's Design Transfer View exports use `IfcAdvancedBrep`.** 176 elements of one Revit 2019 DTV model and one door of a Revit 2027 export are NURBS B-reps. The own reader meshes none of them. Reference View exports, and everything structural in the corpus, are extrusions, faceted B-reps and tessellations, which it handles.
- **Native import needs parameters, not meshes.** #141 turns `IfcExtrudedAreaSolid` with a rectangular or circular profile into a HITO column or beam. That mapping reads the IFC entities, whichever reader is used. ifc-lite's value is its mesh pipeline, which only linked references and the unmapped remainder need.
- **ifc-lite's Rust API changes constantly.** 94 releases in 2026, 18 of them new major versions. Its own release metadata lists 10 breaking changes that affect only the Rust crates, made while the npm packages stayed compatible: the Rust crates are a by-product of a TypeScript and WebAssembly viewer. About 4,000 commits in the last 90 days, by two people (one at LTplus AG, one independent consultant), much of it AI-assisted.
- **ifc-lite brings its own geometry kernel.** It removed Manifold for an in-house exact-arithmetic CSG kernel and returns `f32` meshes, with the site rotation removed. HITO would have two boolean engines and two frames to reconcile.
- **Per-element use of ifc-lite is easy to get wrong.** Called element by element through its router, it gave wrong volumes on a Revit model in feet; its whole pipeline gave the right ones.

## Decision

### 1. Our own reader, in the Part 21 crate

The STEP Part 21 crate of #116 gets a **reader** next to its writer: one pass that indexes every instance by id and type, and decoding on demand. Pure Rust, no dependencies, and written for untrusted input: no panics on malformed bytes, bounded nesting, no allocation sized by a number read from the file. It's fuzzed in CI.

### 2. The IFC mapping and geometry live in HITO

An **IFC import adapter** behind the importer port ([ADR 0004](0004-unified-core-ports-and-adapters.md)) reads units, placements, the spatial structure, types, materials and property sets, and maps elements to HITO elements as #141 and #135 describe. Geometry it can't map to parameters becomes reference geometry:

- Profiles, extrusions, revolutions and sweeps are evaluated by our own code, as ADR 0014 assigns them.
- Faceted B-reps, surface models and tessellated sets become meshes directly.
- Booleans, half-space clippings and openings go to the geometry port (Manifold).
- **Advanced B-rep** (NURBS faces) needs a tessellator. It's required for Revit's Design Transfer View exports, so it's a story for M1. ADR 0014 left exact B-rep to a later adapter; tessellating NURBS surfaces into meshes doesn't need one.

### 3. ifc-lite isn't a dependency, and MPL-2.0 isn't added to `deny.toml` for it

ifc-lite's license isn't the problem: MPL-2.0 is file-level copyleft, and using it unmodified is compatible with [ADR 0009](0009-license.md). The reasons are the API churn, the size, and the second geometry kernel. Whether to allow MPL-2.0 in general stays with the DWG codec spike ([#126](https://github.com/hito-project/hito/issues/126)).

ifc-lite and IfcOpenShell are used as **reference readers in CI**: the importer's meshes are compared with theirs on the corpus. They run as tools outside the workspace, as IfcOpenShell already does for export (ADR 0016), so they don't affect the license.

### 4. Re-evaluate if

- the advanced B-rep tessellator turns out much larger than the rest of the geometry, or
- ifc-lite publishes a stable, separately versioned geometry crate.

Then adopting `ifc-lite-geometry` for the meshes of linked references can be reconsidered by a new ADR, which would also add MPL-2.0.

## Consequences

- HITO controls IFC import completely, and import and export share one Part 21 crate and are tested against each other ([ADR 0021](0021-ifc-import-in-m1.md)).
- The reader itself is small. The IFC geometry is the larger job: the prototype covers 98.5% of the corpus in about 1,750 lines, and the rest (advanced B-rep, sectioned solids, IFC 4.3 alignment geometry) is long-tail work that can follow real files.
- Linked references can be shown before native import exists, using the same reader.
- We need a corpus of real Revit exports, including IFC4 structural models in Reference View and Design Transfer View from three Revit versions. The public corpus has only one Revit structural model, in IFC2X3.
- CI needs IfcOpenShell (already there for export) and a small ifc-lite command-line tool built outside the workspace.
- New work, proposed as stories under E22 (#66): the Part 21 reader, the IFC geometry evaluation behind the geometry port, advanced B-rep tessellation, the IFC corpus with differential tests and fuzzing in CI, and the Revit export corpus.
